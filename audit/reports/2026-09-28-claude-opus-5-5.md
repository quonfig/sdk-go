# sdk-go audit — 2026-09-28

## Verdict
The core is careful and well commented. Hot-path panics are caught, decode is per-entry, the ordering guard is simple and correct, and telemetry never blocks. I would not run it in production until two reproduced defects are fixed. First, SSE connection-state edges are delivered on separate goroutines. A stream that connects and drops quickly can leave the SDK believing it is "connected" for good. The fallback poller then never engages, and config freezes for the whole stream outage (reproduced in 14 of 40 client-level runs). Second, a weighted rollout serves its first variant even when that variant has 0% weight, if the context lacks the hash property (reproduced). There are also five medium defects, all reproduced: a goroutine leak when Close runs during init (it makes one of the repo's own tests flaky under -race), a documented-safe callback that deadlocks, silent zero values on type mismatch, a telemetry data race on nested context values, and datadir silently dropping bad files. I am confident in the findings: each one below has a repro or a direct code citation.

## Findings

### [HIGH] SSE state edges are delivered out of order, so the fallback poller can stay disengaged for a whole outage
- Where: sse_client.go:457-469 (`go cb(v)`), consumed by quonfig.go:857-871 / 935-958 and fallback_poller.go:84-102
- What: `setConnected` fires each connected/disconnected edge in its own goroutine. Two edges fired close together (a stream that returns 200 and then ends at once) run in scheduler order, not in order sent. Go's runnext slot usually runs the newest goroutine first. The final state given to the fallback poller and the supervisor is then `connected=true`. If later reconnects fail before sending 200 (refused, 5xx, DNS), no new edge ever arrives. The poller's engage timer was cancelled by the stale `true`, so Layer 2 never engages.
- Why it matters: this is the outage case the fallback poller exists for, for example a delivery restart that accepts a connection and drops it, then stays down or returns 503 on the stream host. HTTP polling (including failover to the secondary) never runs. Config stays frozen at the last value until the stream recovers or the process restarts. `ConnectionState()` reports `connected` the whole time, so health checks built on it are wrong too.
- Evidence: two repros.
  - Unit level (`zz_audit_edge_order_test.go`): 3000 trials of a stream that returns 200 then closes, with later connects answering 503. The last delivered edge was `true` in **2090/3000** runs.
  - Client level (`zz_audit_poller_stuck_test.go`): `NewClient` with test threshold 50ms and interval 20ms. The first SSE connect returns 200 and closes, and later ones return 503. After 700ms the poller was not engaged in **14/40** runs, e.g. `run 0: poller not engaged; state=connected sse_connects=2 config_fetches=1`.
  - The chaos scenario 09-flapping (passes) ends with the stream healthy, so it cannot catch this.
- Suggested fix: deliver edges in order from one goroutine: call the callback synchronously, or send it through a single-consumer ordered channel. Or have the consumer read the current `connected` state rather than trust the edge value.

### [HIGH] Weighted rollout serves a 0%-weight first variant when the hash property is missing (or none is configured)
- Where: evalcore/weighted.go:36-51 and 67-84 (`getUserFraction` returns 0; `float64(runningSum) >= threshold` matches entry 0 even when its weight is 0)
- What: When `hashByPropertyName` is empty, or the property is absent from the context, fraction = 0 and threshold = 0. The first entry matches because `0 >= 0`, whatever its weight. The "serve the first variant" rule when the property is missing is a documented decision. But the code does not skip zero-weight entries, so a rollout at 0% for variant A serves A to every context that lacks the hash property. With an empty `hashByPropertyName` it serves A to everyone.
- Why it matters: `[{true, 0}, {false, 100000}]` is a valid weight set (it sums to 100000) and a natural "0% rollout" state. Anonymous or partial contexts (no `user.key`) then get the feature that is meant to be off for everyone. The only signal is one WARN per key per process, and none at all when `hashByPropertyName` is empty. I rated this High, not Critical, only because it needs this data shape plus contexts missing the property.
- Evidence: `zz_audit_zero_weight_test.go` in evalcore: `missing hash prop -> idx=0 value=true` and `no hash prop configured -> idx=0 value=true` for weights `[0, 100000]`. Zero-weight entries do occur upstream: app-quonfig's own test fixture `src/lib/domain/flag-status.test.ts:243` has `weight: 0`.
- Suggested fix: on the fallback path, serve the first entry with weight > 0 (and use `>` against a strictly positive threshold, or skip zero-weight entries in the running-sum loop). Add a shared contract case for it.

### [MEDIUM] Close() during initialization leaks the supervisor/fallback poller (WaitGroup Add/Wait race)
- Where: quonfig.go:722-733 and 818-832 (`c.sup = sup` published, then `sup.workers = append(...)` and `sup.Start()` with no `closeCh` check); supervisor.go:110-128
- What: `startBackgroundWorkers` runs on the init goroutine after the first fetch. Unlike `startSSE`, it never checks `closeCh`. If `Close()` runs first, the poller still starts after Close, and nothing ever stops it. If Close runs in between, `supervisor.Stop` calls `wg.Wait()` while `Start` calls `wg.Add(1)`, a WaitGroup misuse data race. Close then returns while the worker keeps running.
- Why it matters: goroutines and network polling outlive `Close()` for any client closed while its first fetch is still in flight: fast shutdown during a slow or failing delivery host, per-tenant or per-request clients, tests. Each leaked client polls every interval forever.
- Evidence:
  - `zz_audit_close_leak_test.go` (first fetch delayed 300ms, Close after 50ms): `config fetches after Close: 4 -> 14; goroutines before=3 now=7`.
  - The repo's own `quonfig_test.go:242 TestNewClientTransportRaceFreeUnderConcurrency` fails under `-race` in 4 of 6 targeted batches. The race report shows the write in `supervisor.Stop.func1` (supervisor.go:127) against the read in `startInitialization.func1` (quonfig.go:732). CI is green on this test by luck.
- Suggested fix: in `startBackgroundWorkers`, add workers before publishing `c.sup`, and check `closeCh` under `c.mu` before `Start` (the same pattern as `startSSE`). Pass a Close-cancelled context into the init fetch.

### [MEDIUM] Calling Refresh() from OnConfigUpdate deadlocks the install path
- Where: quonfig.go:1110-1126 and 909-928 (installEnvelope called with `refreshMu` held); quonfig.go:1303-1305 (callback invoked inside installEnvelope); options.go:115-119 (doc: "safe to call client methods from within the callback")
- What: `OnConfigUpdate` runs while the caller holds `refreshMu`. `Refresh()` -> `fetchAndInstall` takes `refreshMu` again on any 200 response. `sync.Mutex` is not reentrant, so the goroutine deadlocks. After that, every other install path (SSE, poller) blocks on `refreshMu` for good, and config freezes. A merely slow callback also stalls every install.
- Evidence: `zz_audit_refresh_deadlock_test.go` -> `deadlock: Refresh() from OnConfigUpdate never returns; calls=1`.
- Suggested fix: invoke `OnConfigUpdate` after releasing `refreshMu` (for example, return a "fire callback" flag to the caller), or dispatch it on a dedicated ordered goroutine. Otherwise correct the doc.

### [MEDIUM] Type mismatch returns a silent zero value with ok=true and err=nil
- Where: quonfig.go:336-378 (e.g. `GetBoolValue` -> `val.BoolValue()`), config.go:54-117
- What: Getters coerce with lossy helpers. A bool getter on a string config returns `false`, and an int getter on a non-numeric string returns `0`, both reported as found with no error. `ErrorCodeTypeMismatch` exists but is only used for ENV_VAR coercion.
- Why it matters: a flag whose type was changed, or a key typo that hits a config of another type, silently evaluates to the zero value instead of the caller's default path.
- Evidence: `zz_audit_typemismatch_test.go` with a string config holding `"true"`: `GetBoolValue = false ok=true err=<nil>; GetIntValue = 0 ok=true err=<nil>; FeatureIsOn = false ok=true`.
- Suggested fix: compare the value's type with the getter's type and return a typed `ErrTypeMismatch` (ErrorCodeTypeMismatch) with ok=false. This is additive, but it changes behavior, so treat it as a minor version.

### [MEDIUM] Telemetry keeps shallow references to caller context values and serializes them later on another goroutine
- Where: telemetry.go:143-152 (`props[k] = v`, shallow), internal/telemetry/example_context_aggregator.go:152-160, serialized in submitter.go:553-587
- What: nested maps and slices inside `NamedContext.Data` are shared with the example-context aggregator and passed to `json.Marshal` up to one sync interval later. A caller that reuses or mutates a nested map after `Get` returns races with the telemetry goroutine. Without `-race` this can be the Go runtime's unrecoverable `concurrent map iteration and map write` fatal error, which is a process crash.
- Evidence: `zz_audit_ctx_race_test.go`: one `GetBoolValue` with `{"user": {"key": "u1", "attrs": map}}`, then mutate `attrs` while `Close()` serializes -> `WARNING: DATA RACE ... encoding/json.mapEncoder.encode()`. I did not produce the non-race fatal error; it is the known runtime behavior for this race.
- Suggested fix: deep-copy context values (or JSON-encode them) at `RecordContext` time, or document that context data must be immutable once passed in.

### [MEDIUM] Datadir mode silently drops config files that fail to parse
- Where: workspace_loader.go:98-128 (per-file errors are appended to `errs` and discarded unless zero configs loaded; walk errors are ignored)
- What: one malformed or half-written JSON file makes that key disappear with no log at all, both at startup and on auto-reload. Callers then get `ErrNotFound` and fall back to defaults. The network path, by contrast, logs a WARN for each skipped entry.
- Evidence: `zz_audit_datadir_test.go` with one good and one truncated file -> `keys=[good] bad ok=false err=config not found; log mentions bad.json: false`.
- Suggested fix: log each skipped file at WARN, as `decodeEnvelope` does. On reload, consider keeping the previous version of a key whose file failed to parse.

### [LOW] The shared contract suite tests duplicate code, not the shipped Client path
- Where: internal/fixtures/test_helpers_test.go:38-54 uses `internal/eval` and `internal/resolver`. Production uses runtime_eval.go and runtime_resolver.go via `Client`.
- What: `internal/eval/evaluator.go` and `internal/resolver/resolver.go` are parallel copies of the conversion layer and the ENV_VAR/decrypt resolver, with their own sentinel errors. They are imported only by fixtures. The contract proves `evalcore`, but not the production converter, reason and variant logic, the resolver, the getters, or the type handling.
- Suggested fix: run the generated cases through `Client` (datadir or a stubbed store), then delete the duplicates.

### [LOW] Dead package with weaker behavior: internal/transport
- Where: internal/transport/client.go
- What: unused. It stores the ETag before decoding and uses an `http.Client{}` with no timeout, the bugs runtime_transport.go explicitly fixed. It invites misuse by future contributors.
- Suggested fix: delete it.

### [LOW] Non-200 response bodies are read unbounded and embedded in errors returned to callers
- Where: runtime_transport.go:292-295
- What: `io.ReadAll(resp.Body)` has no size limit (only the 6s per-leg abort bounds it). The whole body, for example a proxy's HTML error page, becomes part of `initializationErr`, which every `Get*` returns during init failure (`ErrorMessage`).
- Suggested fix: use `io.LimitReader(resp.Body, 4096)`, as the SSE path and telemetry already do.

### [LOW] Hot-path cost: per-call config conversion, context copy, and regex compilation
- Where: runtime_eval.go:27-33 (`configResponseToShared` on every evaluation, plus again for each segment); quonfig.go:595-598 (context copied for telemetry on every call); evalcore/operators.go:113 (`regexp.Compile` per PROP_MATCHES evaluation)
- What: 13-21 allocations and ~1 KB per `Get`. Acceptable for most services, but it is avoidable GC pressure at high QPS. Convert once at install time and cache compiled regexes.

### [LOW] Dev-context injection is on by default in every process
- Where: options.go:352-364, dev_context.go
- What: `NewClient` reads `~/.quonfig/tokens.json` and, if present, merges `quonfig-user.email` into every evaluation, including example-context telemetry. It is inert only where that file is absent. A production host or shared runner where someone ran `qfg login` would evaluate targeting with a developer's identity. This is documented, but the default is surprising for a server SDK.

### [LOW] Contract-sync gaps in CI
- Where: .github/workflows/test.yaml:33 pins `v2026.05.20`; internal/fixtures/delivery_environment_generated_test.go comes from `tests/eval/delivery_environment.yaml`, which only exists from v2026.06.19.1 on.
- What: the generator writes files but never deletes them, so the "in sync" check cannot detect orphaned or newer generated files. `TestMain` also accepts 0 loaded configs: 70 of 187 fixture tests pass with no data at all.
- Suggested fix: bump the pin. Delete `*_generated_test.go` before regenerating in CI. Fail `TestMain` when `configStore.Len()==0`.

### [LOW] Integration tests can't run outside the monorepo, and one has an undeclared env dependency
- Where: integration_test.go:34-36, 144-345
- What: non-short tests need the private `api-delivery` sibling. `TestIntegration_FrontendFiltering` also needs `REFORGE_INTEGRATION_TEST_ENCRYPTION_KEY` in the environment. CI never runs these (`-short`). Also, the contract case "get_or_raise can raise an error if value not found" (get_or_raise_generated_test.go:13) only asserts the key is absent from the store, not that the SDK returns an error.
