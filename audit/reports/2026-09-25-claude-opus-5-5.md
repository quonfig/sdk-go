# sdk-go audit — 2026-09-25

## Verdict

I would not run this version in production as-is if I used percentage (weighted) rollouts. Concurrent evaluation of a weighted rollout, when the context lacks the hash property, shares one `math/rand.Rand` across goroutines. I reproduced an `index out of range` panic through the public `GetBoolValue` within seconds, which crashes the whole process. Apart from that, the code is careful and well commented, CI is serious (race detector, vet, staticcheck, govulncheck, a generated contract suite), and evaluation does no I/O after init. But the resilience story has holes the vendor's tests don't reach. The fallback poller never starts if the SSE stream never connects (or SSE is disabled). A 200 response with any non-envelope JSON body wipes every flag to defaults. And several malformed-config inputs crash the process. I'm highly confident in the Critical and High findings: each one has a runnable reproduction, and the code excerpts are below. Fix C1 and H1–H3 first, and this would be a solid B.

## Findings

### [CRITICAL] C1 — Concurrent weighted-rollout evaluation shares a non-thread-safe `*rand.Rand` and can panic the caller

- **Where:** `evalcore/weighted.go:10-17,70`; `evalcore/evaluator.go:38` (one resolver per Evaluator); `runtime_eval.go:13-17` (one Evaluator per installed envelope, shared by every goroutine calling Get).
- **What:** `WeightedValueResolver.getUserFraction` falls back to `w.rng.Float64()` when `hashByPropertyName` is unset or absent from the context. `w.rng` is `rand.New(rand.NewSource(seed))`, which is documented as not safe for concurrent use. Concurrent calls race on `rngSource.tap`/`feed` and can index `vec` out of range.
- **Why it matters:** An unrecovered panic in the caller's goroutine kills the whole process. The trigger is common: a percentage rollout evaluated for requests without the hash key (anonymous traffic, background jobs, a missing `user.key`) under normal concurrency. Nothing on the Get path recovers panics.
- **Evidence:** Scratch-copy test with 32 goroutines calling `c.GetBoolValue("rollout", nil)` on a 50/50 `weighted_values` flag with `hashByPropertyName: "user.key"`:
  ```
  panic: runtime error: index out of range [-1]
      evalcore/weighted.go:70
      evalcore/weighted.go:29
      quonfig.go:518   (resolveDetail -> EvaluateConfigResponse)
      quonfig.go:456
      quonfig.go:349   (GetBoolValue)
  ```
  - It reproduced in 2 of 2 runs (1M iterations per goroutine). Calling `Resolve` directly panicked in 3 of 3 runs within about 1s.
  - `go test -race` reports `WARNING: DATA RACE … math/rand.(*rngSource).Uint64 … evalcore/weighted.go:70` at 20k iterations.
  - No existing test evaluates weighted values concurrently. `eval_bench_test.go` has no `RunParallel`.
- **Suggested fix:** Use the goroutine-safe top-level `math/rand/v2` functions (or guard `rng` with a mutex), and add a concurrent weighted-eval test under `-race`. Also consider a `recover` at the `resolveDetail` boundary that returns the caller's default plus an error.

### [HIGH] H1 — The fallback poller never engages if the SSE stream never connects, or when `WithSSE(false)`

- **Where:** `fallback_poller.go:151-165` (engagement only after a `false` edge arrives on `stateCh`); `sse_client.go:84-90,410-428` (initial `connected=false`, so a failing connect produces no edge); `quonfig.go:668-725` (nothing seeds the poller); `options.go:815-826` (the doc promises otherwise).
- **What:** The engage timer starts only on `SetSSEConnected(false)`, and that is only called on a connected→disconnected transition. The poller never engages in two cases:
  - The stream host is unreachable, returns non-200, or is filtered from the moment the client starts.
  - SSE is disabled. The startup log still announces `mode=fallback-poll-only`.

  The `WithSSE` doc says the poller "engages immediately when there is no SSE stream to be connected to". It doesn't.
- **Why it matters:** SSE is pinned to the *primary* stream host (`quonfig.go:736`). If a customer's app starts during a primary-region outage, the HTTP hedge gets config from the secondary, SSE never connects, and the client never refreshes again until the primary comes back. That is exactly the failure the secondary exists for. The same happens behind proxies or firewalls that break streaming, and for anyone who chose `WithSSE(false)` expecting polling. `ConnectionState()` stays `initializing` forever.
- **Evidence:** Scratch test `TestAudit_R3` with `WithFallbackPoll(true, 1s)`, a server counting `/api/v2/configs` hits, and a 130 s wait (past the hard-coded 120 s threshold):
  ```
  A (SSE never connects): config GETs=1, FallbackPollerActive=false, state=initializing
  B (WithSSE(false)):    config GETs=1, FallbackPollerActive=false, state=initializing
  ```
  None of the chaos scenarios cover this, because they all assert `connected` within 5 s first. f01 disables SSE but only runs 15 s.
- **Suggested fix:** Start the engage timer when the poller starts (or on the first failed connect attempt), and engage immediately when SSE is disabled. Add a test with the stream never connecting.

### [HIGH] H2 — Any JSON object in a 200 response (or SSE event) replaces the whole config set, bypassing the ordering guard

- **Where:** `runtime_transport.go:295-301` (decodes any JSON object into `ConfigEnvelope`, no validation); `quonfig.go:1099-1109` (`Generation <= 0` always installs); `quonfig.go:1150-1175` (installs and sets `heldGeneration = 0`); SSE path `sse_client.go:309-317`.
- **What:** A 200 body like `{"error":"upstream maintenance"}` or `{}` decodes to an empty envelope with generation 0. The "unversioned" carve-out installs it even on an established client. After that, `heldGeneration` is 0, so a stale older snapshot (for example from a lagging secondary) is also accepted.
- **Why it matters:** The client silently serves caller defaults for every key instead of the last known values. The trigger is a misbehaving proxy or CDN, a delivery bug, or a maintenance page that returns JSON with 200. This contradicts both "worst case is last known values" and "never replaces newer with older".
- **Evidence:** Scratch test `TestAudit_NonEnvelope200Wipes`:
  ```
  before: flag.bool=true ok=true keys=2 gen=7
  after 200 {"error":...}: Refresh err=<nil> flag.bool=false ok=false err=config not found keys=0 gen=0
  ```
- **Suggested fix:** Validate the envelope before install: require `meta.version` and a non-nil `configs`, and reject an empty envelope replacing a non-empty one unless the server marks it explicitly. Never let an unversioned payload lower a positive held generation.

### [HIGH] H3 — Malformed config data crashes the process (three paths, none recovered)

- **Where:**
  - (a) `evalcore/evaluator.go:135-148`: segment resolution recurses with no cycle or depth guard.
  - (b) `runtime_resolver.go:63-74`: `decryptWith` key resolution recurses into `ResolveValue` with no guard.
  - (c) `internal/encryption/encryption.go:57-59`: `dataToProcess[:len-gcm.Overhead()]` with no length check.
- **What and evidence:**
  - (a) A segment whose rule is `IN_SEG` itself (or A→B→A). Scratch test result: `runtime: goroutine stack exceeds 1000000000-byte limit / fatal error: stack overflow`. This is a *fatal error*, and `recover` cannot catch it.
  - (b) A decryption-key config that is itself `confidential` with `decryptWith` pointing at itself gives the same unbounded recursion. I found this by reading the code, not by running it.
  - (c) `DecryptValue(key, "AA--00112233445566778899AABB--BB")` gives `panic: runtime error: slice bounds out of range [:-14]`. It is reached from `GetStringValue` through `resolveDetail → ResolveValue → resolveDecryption`.
- **Why it matters:** One bad record in the workspace kills every process that evaluates the affected key. In datadir mode the input is a hand-editable git checkout, so the server can't validate it. In delivery mode, protection depends entirely on server-side validation I could not see. I rated this High rather than Critical only because it needs malformed data.
- **Suggested fix:** Pass a visited set or depth limit through segment and decryption-key resolution, returning no-match or an error. Check `len(dataToProcess) >= gcm.Overhead()` and a non-empty IV.

### [MEDIUM] M1 — SSE connection edges can reach the poller and supervisor in reverse order

- **Where:** `sse_client.go:417-428` (`go cb(v)` per edge).
- **What:** Each connected/disconnected edge fires its callback on a new goroutine, so a fast connect→drop can be observed as drop→connect. The fallback poller then believes SSE is up and disengages or never arms, and `ConnectionState()` reports `connected`. Later failing connects produce no edges, so nothing corrects the state.
- **Why it matters:** This is a silent loss of fallback polling after a quick accept-then-close, for example from an LB or proxy returning 200 and closing, or from the M2 case.
- **Evidence:** Scratch test `TestAudit_R6` calls `setConnected(true)` then `setConnected(false)` and records the order in which callbacks run: `final observed state=connected in 1966/2000 trials`. The Go scheduler runs the newest goroutine first, so reversal is the norm for back-to-back edges.
- **Suggested fix:** Deliver edges on a single ordered channel or goroutine, or include a sequence number and drop stale edges.

### [MEDIUM] M2 — An SSE event larger than 4 MiB causes a tight reconnect loop, and fallback never engages

- **Where:** `sse_client.go:302-303` (`maxLine = 4 MiB`), `:343` (`_ = scanner.Err()`, not logged), `:258-262` (returns "was connected"), `:178-181` (backoff reset).
- **What:** When the envelope exceeds 4 MiB, `bufio.Scanner` fails with `ErrTooLong`. `connectOnce` still returns `true`, so backoff resets to 500 ms and the client reconnects every 0.25–0.5 s, re-downloading at least 4 MiB each time. Nothing installs. Because every reconnect is a connect edge, the 120 s fallback timer keeps resetting and the poller never engages. Nothing is logged.
- **Why it matters:** When a workspace grows past about 4 MiB (the limit is undocumented), every client freezes on its init snapshot and hammers api-delivery.
- **Evidence:** Scratch test `TestAudit_R7` against a server that sends one 5 MiB `data:` line: `27 SSE connections in 10s, 0 envelopes delivered`. Malformed JSON events are also dropped silently (`sse_client.go:311-317`).
- **Suggested fix:** Treat a scanner error as a failed connect (apply backoff and log a WARN), raise or configure the limit, and let the poller engage on repeated failures.

### [MEDIUM] M3 — The ETag is stored before the body is decoded, so one truncated 200 pins a stale config

- **Where:** `runtime_transport.go:289-298`.
- **What:** The leg's ETag slot is updated before `json.Decode` succeeds. After a truncated or garbled 200, the next poll sends `If-None-Match` with the new ETag, gets a 304, and the SDK treats its older config as current. `LastSuccessfulRefresh` keeps advancing.
- **Why it matters:** While on the poll path (SSE down), a mid-body network cut leaves the client stale until the next config change or an SSE reconnect. Health checks based on `LastSuccessfulRefresh` look fine throughout.
- **Evidence:** Scratch test `TestAudit_R8`: `refresh1 err=decoding response: unexpected EOF / refresh2 err=<nil> refresh3 err=<nil>; HeldGeneration=5 (server is at 6)`.
- **Suggested fix:** Write the ETag only after a successful decode and install decision.

### [MEDIUM] M4 — `OnConfigUpdate` runs under `refreshMu`, and calling `Refresh()` from it deadlocks

- **Where:** `quonfig.go:1172-1174` (callback invoked inside `installEnvelope`), with callers holding `refreshMu` at `:798`, `:996` and `:317`; `options.go:115-118` says it is "safe to call client methods from within the callback".
- **What:** `Refresh` → `fetchAndInstall` → `refreshMu.Lock()` blocks forever when called from the callback on a 200. On the init path the init goroutine hangs, so SSE and the poller never start. More generally, any slow callback stalls every install path.
- **Evidence:** Scratch test `TestAudit_R4`: `DEADLOCK: Refresh inside OnConfigUpdate did not return within 5s; ConnectionState=initializing`.
- **Suggested fix:** Invoke the callback after releasing `refreshMu` (or on a dedicated goroutine), or document the restriction.

### [MEDIUM] M5 — Typed getters silently return zero values on a type mismatch

- **Where:** `config.go:52-100` (`BoolValue`/`IntValue`/`DoubleValue` default to zero); `quonfig.go:329-407`; `errorCodeFor` maps only `ErrUnableToCoerce` (env-var coercion) to `TYPE_MISMATCH`.
- **What:** `GetIntValue` on a bool flag returns `(0, true, nil)`. `FeatureIsOn` on a string flag returns `(false, true)`. `EvaluateDetails` reports `ErrorCode ""`.
- **Why it matters:** Changing a config's value type in the UI, or a key typo that collides with another config, makes the app use a zero value while the SDK claims the key was found. The customer's default is never used.
- **Evidence:** `TestAudit_R2`: `GetIntValue(bool flag) = 0 ok=true err=<nil>`, `GetFloatValue(bool flag) = 0 ok=true err=<nil>`, `EvaluateDetails errorCode=""`.
- **Suggested fix:** Check `Value.Type` or `cfg.ValueType` in each typed getter and return a `TYPE_MISMATCH` error with `ok=false`.

### [MEDIUM] M6 — Returned slices and maps alias the SDK's internal store

- **Where:** `quonfig.go:365-398` (`GetStringSliceValue`, `GetJSONValue` return `val.Value` directly); `runtime_eval.go` copies only the `Value` struct.
- **What:** If a caller mutates a returned `[]string` or JSON map, every later evaluation for every goroutine sees the mutation (until the next install), and the write races with concurrent readers.
- **Evidence:** `TestAudit_ReturnedValuesAliasStore`: after `l[0]="MUTATED"` and `obj["limit"]=999`, the next Gets return `list=[MUTATED b] obj=map[limit:999]`.
- **Suggested fix:** Return copies (a deep copy for JSON), or document the values as read-only.

### [MEDIUM] M7 — Datadir mode silently drops config files that fail to parse

- **Where:** `workspace_loader.go:110-129`.
- **What:** Per-file parse errors are collected but discarded whenever at least one file parsed. Nothing is logged. On auto-reload (`reloadDatadir`), a bad commit or a half-written file makes that flag disappear. The "parse failed, keep old envelope" path only triggers when *every* file fails.
- **Why it matters:** Flags silently fall back to caller defaults in datadir deployments, and nothing in the logs says why.
- **Evidence:** `TestAudit_DatadirSilentDrop` with one valid and one truncated JSON file: `NewClient err=<nil>`, `keys=[a]; Get(b) ok=false err=config not found`, no log output.
- **Suggested fix:** On reload, reject the whole reload if any file fails (keep the old envelope). At init, log each parse error at WARN or ERROR, or fail.

### [LOW] L1 — `Close()` during initialization leaks goroutines, and a WaitGroup race trips `-race`

- **Where:** `quonfig.go:624-635,668-720` (`startBackgroundWorkers` never checks `closeCh`); `supervisor.go:108-131`.
- **What:** If `Close()` runs while the init fetch is in flight, the init goroutine then builds and starts a supervisor and poller that nothing will ever stop. The in-flight fetch also isn't cancelled by Close. When the timing overlaps, `sup.Start()` (`wg.Add`) runs concurrently with `sup.Stop()` (`wg.Wait`), which the race detector flags.
- **Evidence:** `TestAudit_R5` ran 50 create/Close cycles during init: `goroutines before=4 after=60; fallbackPoller.Run goroutines alive=50`. `TestNewClientTransportRaceFreeUnderConcurrency` failed once in 20 iterations with `WARNING: DATA RACE … supervisor.Stop.func1 … startInitialization.func1 quonfig.go:634`.
- **Suggested fix:** Check `closeCh` under `mu` before starting the supervisor, and use a cancelable context for the init fetch.

### [LOW] L2 — The shared contract tests exercise test-only adapters, not the production glue

- **Where:** `internal/fixtures/test_helpers_test.go:245-261,517-577`; `internal/fixtures/aggregator_helpers_test.go:264-287`; the production equivalents are `runtime_eval.go`, `runtime_resolver.go` and `telemetry.go`.
- **What:** Generated tests call `internal/eval` and `internal/resolver`, a second adapter and resolver used only by tests. They don't go through `runtimeEvaluator`, `runtimeResolver` or `Client`, except for the init-timeout cases. Telemetry "reason" contract cases compute the reason in the harness, and the harness logic differs from production: SPLIT is `WeightedValueIndex > 0` in the harness versus `IsWeighted` in production (`runtime_eval.go:56-63`). A regression in production reason or value-resolution code would keep the contract green. `internal/resolver` even defines its own `ErrUnableToCoerce` sentinel, distinct from `quonfig.ErrUnableToCoerce`.
- **Suggested fix:** Drive the generated cases through `quonfig.Client` (for example with a datadir or in-memory envelope) and delete the duplicate adapters.

### [LOW] L3 — CI pins have drifted, and the regen gate can't detect extra fixture files

- **Where:** `.github/workflows/test.yaml` (`ref: v2026.05.20`), `chaos.yaml` (`v2026.05.13`), `failover-chaos.yaml` (`v2026.06.19.1`); `go.mod` (`go 1.23`).
- **What:**
  - The committed fixtures are exactly the v2026.06.19.1 output.
  - The pinned v2026.05.20 does not generate `delivery_environment_generated_test.go`, but `git diff --exit-code internal/fixtures/` can't notice an extra committed file, so the gate passes against a tag that isn't the source.
  - integration-test-data `main` fails to generate Go (`unsupported YAML type: BOOL`), so the pin can't move forward.
  - `go.mod` allows Go 1.23 and 1.24, but CI only tests 1.25 and 1.26.
- **Suggested fix:** Bump and align the pins, have the gate delete `*_generated_test.go` before regenerating, and add 1.23 to the matrix or raise the `go` directive.

### [LOW] L4 — Flaky unit tests

- **Where:** `fallback_poller_test.go:147-190`; the race described in L1.
- **What:** `TestFallbackPollerDisengagesOnReconnect` failed in each of 3 runs with `-count=5` (`expected exactly 1 disengage callback, got 0`). `fallback_poller.go:110-118` clears `active` before calling `OnDisengage`, and the test reads the counter in between. It uses 5 ms thresholds. This is a test bug, not a product bug, but it will turn CI red intermittently.
- **Suggested fix:** Wait on the callback count rather than `Active()`.

### [LOW] L5 — Telemetry uploads raw context attribute values by default, with no per-attribute redaction

- **Where:** `options.go:251` (default `ContextTelemetryPeriodicExample`); `telemetry.go:161-172`; `internal/telemetry/example_context_aggregator.go:36-107`.
- **What:** Up to 10,000 distinct full contexts per minute are sent: every attribute value, such as email, IP or plan. The README lists "example contexts" but doesn't say that values leave the process, and there is no private-attribute option. The copies are shallow, so nested maps or slices are shared with the caller and marshaled later on another goroutine.
- **Mitigation:** Documented opt-outs exist (`ContextTelemetryShapes`, `WithAllTelemetryDisabled`). Confidential *config* values are redacted to `*****<md5 prefix>`. I found no API-key logging: keys go only into Basic auth headers.
- **Suggested fix:** Document explicitly that attribute values are sent, add private-attribute redaction, and deep-copy.

### [LOW] L6 — Dead and duplicated code

- **Where:** `internal/transport/client.go` (no importers); `runtimeTransport.FetchConfigs` (not used on the production path); `internal/eval`, `internal/resolver`; `reportableValueFor` duplicated in `telemetry.go` and `internal/resolver`; reason logic duplicated in test helpers; `regexp.Compile` on every `PROP_MATCHES` evaluation (`evalcore/operators.go:113`).
- **Why it matters:** An outside maintainer has to work out which of two near-identical implementations actually ships. L2 shows they have already drifted.

### [LOW] L7 — Blocking and panicking edges of the public API

- **What:**
  - Before init completes, every Get blocks for up to `InitTimeout` (10 s by default). That includes the `slog` handler's `Enabled` (`slog.go:143`), so application logging stalls at startup when delivery is unreachable.
  - `ReturnZeroValue` only applies to timeouts. A fast init failure (DNS, 401) still returns an error (`quonfig.go:465-479`).
  - `ShouldLogPath` and `NewQuonfigHandler` panic by design when `LoggerKey` is unset.
  - Non-200 bodies are read unbounded into error strings (`runtime_transport.go:285`), and 200 bodies are decoded with no size limit. Both are time-bounded only by the 6 s hedge abort.
  - A zero-value `ContextSet{}` panics on `WithNamedContextValues` (nil map).

## Test suite assessment

- **Volume and result.** 597 tests pass under `-race -short`. The suite is large, and in places it is thoughtful: ordering guard, hedge, telemetry transport contract T1–T8, SSE parser fuzzing, duration fuzzing and envelope fuzzing.
- **Contract coverage.** I spot-checked these against their YAML:
  1. Weighted consistent hashing (`get_weighted_values`): asserts exact bucket values.
  2. Context precedence, global versus local clobber (`context_precedence`): asserts true or false.
  3. Init timeout under `on_init_failure: raise` (`get_or_raise`): goes through a real `NewClient` with a blocking RoundTripper and `errors.Is(ErrInitializationTimeout)`.
  4. Missing env var, coercion and decryption errors: asserted with `errors.Is`, but against `internal/resolver` sentinels, not production.
  5. Telemetry reason STATIC/TARGETING/SPLIT: asserted, but the reason is computed by test-harness code, not production (L2).

  None are skipped or weakened: no `t.Skip` in `internal/fixtures`. The weakness is structural. The contract proves `evalcore` operators, but not `runtime_eval`/`runtime_resolver`/`Client`.
- **Behaviors outside the shared suite.**
  - No concurrency in evaluation, which is how C1 went unnoticed.
  - SSE never connecting at startup, or `WithSSE(false)` polling (H1).
  - Edge ordering (M1), oversize SSE lines (M2), truncated-body ETag (M3).
  - Non-envelope 200s (H2), segment or decryption cycles and short ciphertext (H3).
  - Type mismatch on typed getters (M5), datadir partial parse failure (M7).
- **Chaos rigs** (read, not run). The scenarios (01–11, f01–f05, o01–o05) are well designed for single-fault injections on a client that started healthy. Every sse_resilience scenario asserts `connected` within 5 s before injecting a fault, so a client that *starts* with SSE broken is never exercised (H1). Scenario 05 would catch a regression in the normal disconnect→engage path. f01 uses `sse_endpoint: disabled` for only 15 s, well under the 120 s threshold. In the Go driver, `TestChaos` calls `t.Skipf` if toxiproxy is unreachable. `run-chaos.sh` starts the harness first, but a harness failure after startup would show as a skip rather than a red run. That risk is minor.
- **Tests that can't fail or are fragile.** The telemetry-reason fixtures can't catch a production regression (L2). The integration tests skip in `-short` and depend on a private sibling repo plus an env var; one fails locally (see What I ran). The fallback poller tests use 5 ms timings and are flaky (L4).
