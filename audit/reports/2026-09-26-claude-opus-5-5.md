# sdk-go audit — 2026-09-26

## Verdict

I would run this SDK in production only after the three High findings are fixed, or with mitigations in place for them. The core design is careful. Evaluation is in-memory and costs about 1µs per call. Background work is supervised. Telemetry is non-blocking and bounded. The generation guard is well reasoned. I found no data races and no goroutine leaks on the normal create/close path. The biggest risks are cliff-edge failures that fail silently:

- An SSE event larger than 4 MiB puts every client into a reconnect storm with frozen config. The fallback poller never engages.
- One malformed value in any one config makes the SDK reject the entire workspace payload.
- `GetJSONValue` / `GetStringSliceValue` return pointers into the shared in-memory store. A caller that mutates the result corrupts config for every caller, or triggers Go's unrecoverable "concurrent map writes" fatal error.

The shared contract suite passes, but it tests a test-only evaluation stack, not the `Client` path customers call. The main suite is green, so the SDK's quality looks better than it is. I have high confidence in the reproduced findings (7 of the 10 High/Medium findings have a reproduction). My confidence is moderate that I found all the High-class issues. I did not run the chaos rigs.

## Findings

### [HIGH] SSE event larger than 4 MiB causes a permanent reconnect storm, and the fallback poller never engages
- Where: sse_client.go:298-345 (`maxLine = 4 MiB`, `scanner.Err()` discarded), sse_client.go:253-262 (`connectOnce` returns true once headers were 200), sse_client.go:176-181 (backoff reset when `connectedOK`), fallback_poller.go:175-186 (each connected edge cancels the engage timer)
- What: When a `data:` line exceeds 4 MiB, `bufio.Scanner` stops with `ErrTooLong`. The SSE client ignores this error. `parseStream` returns and `connectOnce` reports that the connection was live, so `runLoop` resets the delay to 500ms and reconnects. The server resends the same oversized snapshot on every connect. Every cycle also emits a connected edge, which cancels the poller's 120s engage timer, then a disconnected edge, which re-arms it. The poller can therefore never reach its threshold.
- Why it matters: Once a workspace's serialized envelope crosses 4 MiB, every Go client in the fleet stops receiving updates. It stays on whatever the init HTTP fetch loaded, because the HTTP path has no size limit. Each client also reconnects about 3 times per second and downloads the full envelope each time, which amounts to a self-inflicted DDoS on api-delivery. Nothing is logged above debug level. Workspaces grow gradually, so this failure arrives suddenly with no warning.
- Evidence: I reproduced it with an httptest server that answers `/api/v2/configs` with a small gen-1 envelope and the SSE path with one ~5 MiB `data:` line, then holds the connection. The client had `withTestFallbackPollThreshold(1500ms)` and `WithFallbackPoll(true, 20ms)`. After 5s the output was `sse connections=14 config fetches=1 fallbackActive=false state=disconnected heldGen=1`. With the default threshold of 120s the poller could never engage.
- Suggested fix: Treat `scanner.Err() != nil` (and any stream that ended without delivering a valid event) as a failed connection, with backoff and no connected edge. Also raise or remove the line cap, or stream-decode the JSON. Log at WARN when an event is dropped.

### [HIGH] One malformed value in any config rejects the whole envelope, on every install path
- Where: config.go:134-239 (`Value.UnmarshalJSON` returns errors, for example config.go:203-205 for a JSON value stored as a string, config.go:162-164 for a non-numeric int), runtime_transport.go:289-292 (the whole decode fails), sse_client.go:310-319 (SSE failures are swallowed with no log), workspace_loader.go (datadir uses the same types)
- What: Decoding is all-or-nothing. A single rule value that fails its type-specific decode, such as a legacy stringified `json` value, `"int"` with `"12a"`, or a `bool` given as a string, fails `json.Decode` for the entire `ConfigEnvelope`.
- Why it matters: Configs live as files in a git repo that people can edit, so a bad value in one config is a realistic event. When it happens:
  - A fresh process fails init. With the default `ReturnError`, every getter for **every** key returns an error.
  - Established clients freeze on their last snapshot.
  - The SSE path drops the event with no log at any level. The HTTP path records the error only as the init error or at debug level in the poller.

  The blast radius is the whole workspace for one bad key.
- Evidence: I served two configs, a valid bool flag `good.flag` and a `json` config whose value is the string `"{\"a\":1}"`. The client returned `good.flag => v=false ok=false err=decoding response: json value must not be a string (legacy stringified form); decode to native JSON`.
- Suggested fix: Decode `configs` as `[]json.RawMessage` and unmarshal each entry independently. Skip and log (WARN, once per key and version) any config that fails, and install the rest. Log dropped SSE events at WARN.

### [HIGH] Getter results alias the shared in-memory config; caller mutation corrupts all callers or crashes the process
- Where: quonfig.go:392-398 (`GetJSONValue` returns `val.Value`), quonfig.go:365-372 (`GetStringSliceValue` returns `StringListValue()`, which is the stored `[]string`), runtime_eval.go:173-175 and 220-222 (`shared.Value = v.Value` and back, with no deep copy), evalcore/evaluator.go:97 (`value := rule.Value // copy` is shallow)
- What: The `map[string]interface{}` and `[]string` values handed to the caller are the same objects held by the installed store. They stay shared until the next install.
- Why it matters: Callers may treat the result as theirs. For example, they might `sort.Strings(list)`, or `m["x"] = y` to merge in defaults. That silently changes the config for every other caller in the process. If two goroutines do it at the same time, Go aborts with `fatal error: concurrent map writes`, which `recover` cannot catch, so the host process dies. The docs do not warn about this ("direct pass-through of Value.Value").
- Evidence: I served `list=["b","a"]` and `obj={"k":"orig"}`, then called `l[0]="MUTATED"` and `j["k"]="MUTATED"` on the returned values. A second read returned `second read list=[MUTATED a] obj=map[k:MUTATED]`.
- Suggested fix: Return a deep copy for JSON, list and map values. Alternatively, freeze values at install time and document them as read-only, but a copy is the safe default at 1.x.

### [MEDIUM] Close() during initialization leaks the supervisor and fallback poller, which keep polling forever
- Where: quonfig.go:654-665 (the init goroutine always calls `startBackgroundWorkers`), quonfig.go:750-764 (stores `c.sup` and calls `sup.Start()` without checking `closeCh`), compared with quonfig.go:818-828, where `startSSE` does check it. Also quonfig.go:236-261: `Close` stops only the `c.sup` it can see.
- What: If `Close()` runs while the init fetch is in flight, `Close` sees `c.sup == nil`. Later the init goroutine creates and starts a supervisor, and nothing ever stops it. With `WithSSE(false)` the poller engages immediately. With defaults it engages after 120s and then polls every 60s. It keeps running for the life of the process, using the SDK key.
- Why it matters: This leaks goroutines and network traffic per client. Services that build and close clients during startup or shutdown, or on reconfiguration, accumulate leaked pollers, and the problem is worst during a delivery slowdown, exactly when init is slow.
- Evidence: The first config response was delayed 300ms, with `WithSSE(false)` and `WithFallbackPoll(true, 20ms)`, and `Close()` was called at 50ms. The output was `config fetches after Close returned: at t+450ms=8, at t+950ms=34` and the test failed with `fallback poller still polling after Close: 8 -> 34`.
- Suggested fix: In `startBackgroundWorkers`, check `closeCh` under `c.mu` before storing and starting the supervisor, as `startSSE` already does. Pass a context that `Close` cancels into the init fetch as well.

### [MEDIUM] An unversioned payload can move an established client backward, and the regression sticks
- Where: quonfig.go:1147-1157 (a payload with `Generation <= 0` always installs), quonfig.go:1209-1216 (`heldGeneration` is not lowered)
- What: The "unversioned carve-out" installs any payload with generation 0 over newer content. Because `heldGeneration` keeps the old value (9 in my test), the primary's next equal-generation payload is rejected as "not strictly newer". The client therefore stays on the stale unversioned content until the primary's generation actually advances. With a per-leg ETag, the primary also answers 304.
- Why it matters: This happens in mixed-version deploys, for example a secondary or proxy that omits `generation`, or a server whose rev-count failed. A hedge that reaches the unversioned leg during a primary blip regresses config, and the primary recovering does **not** heal it. This contradicts the claim "never replaces a newer config with an older one" for anything outside the versioned path. The carve-out is documented. The sticky consequence is not.
- Evidence: The primary serves `k=NEW` at gen 9, the secondary serves `k=OLD` with no generation. After the primary returns 503 once and then recovers, the output was `init=NEW after-primary-blip=OLD after-primary-recovers=OLD heldGen=9`.
- Suggested fix: After an unversioned install, mark the held state as unordered, so that the next versioned payload with `Generation >= heldGeneration` installs. Alternatively, never let an unversioned payload replace a versioned one on an established client.

### [MEDIUM] OnConfigUpdate runs while the install lock is held; calling Refresh() from it deadlocks every install path
- Where: quonfig.go:1042-1053 and quonfig.go:841-860 (`installEnvelope` is called under `refreshMu`), quonfig.go:1227-1229 (the callback is invoked synchronously inside it), options.go:727-736 (no warning in the docs)
- What: `refreshMu` is a non-reentrant `sync.Mutex`. If the user callback calls `c.Refresh()`, it blocks forever on `refreshMu`. After that, every later install (SSE, poller, Refresh) blocks behind it. A merely slow callback also stalls the SSE reader goroutine.
- Why it matters: Config freezes silently. The process still serves the last values, but nothing ever updates again. "Refresh on change" and "re-read everything on change" are natural things to put in this hook.
- Evidence: A callback calls `c.Refresh()` on its second invocation, and the test then triggers a Refresh. Output: `DEADLOCK: Refresh() called from OnConfigUpdate never returned (refreshMu held)` after 3s.
- Suggested fix: Invoke `OnConfigUpdate` after releasing `refreshMu`, for example on a dedicated goroutine with coalescing. At minimum, document that the callback must not call back into the client.

### [MEDIUM] SSE connection-state edges are delivered on separate goroutines and can arrive out of order
- Where: sse_client.go:418-429 (`go cb(v)` for each edge), which feeds quonfig.go:789-803 → `handleSSEStateChange` and `fallbackPoller.SetSSEConnected`
- What: A quick connect/drop pair (true, then false) runs as two independent goroutines. Go does not guarantee their order. If "false" is handled first and "true" last, the poller records `sseConnected=true` and stops its engage timer, and the supervisor reports `connected`. If the following reconnects fail, `setConnected(false)` emits no new edge because the state is already false internally, so the poller never engages.
- Why it matters: Config freezes silently and `ConnectionState()` reports the wrong state after a flap followed by an outage. A 200-then-immediate-close, as from some proxies or from the oversized-event case above, widens the race window.
- Evidence: Code reading only. I did not reproduce this; it is a scheduling race.
- Suggested fix: Deliver edges through a single ordered channel and consumer, or call the internal bookkeeping synchronously and put only the user callback on a goroutine.

### [MEDIUM] The contract suite does not exercise the production evaluation path, and the harness has already drifted from it
- Where: internal/fixtures/test_helpers_test.go:38-58 (`TestMain` wires `internal/eval` + `internal/resolver`, not `Client`/`runtimeEvaluator`/`runtimeResolver`), test_helpers_test.go:517-553 and aggregator_helpers_test.go:262-298 (reason and type mapping re-implemented "same logic as runtime_eval.go"), telemetry.go:93 (production sends `string(result.ConfigType)`)
- What: All ~187 generated cases call a parallel stack: `internal/eval` and `internal/resolver`, which duplicates runtime_resolver.go line for line. None of them go through `NewClient`, `resolveDetail`, `runtimeEvaluator`, `runtimeResolver`, `reportableValueFor`, or `telemetrySubmitter.RecordEvaluation`. The harness also computes telemetry fields itself, and it already disagrees with production:
  - Type casing: the harness sends `FEATURE_FLAG`/`CONFIG`, as the YAML expects (telemetry.yaml:39, 60, 85). Production sends lowercase `feature_flag`.
  - The harness's SPLIT test is `WeightedValueIndex > 0`. Production uses `IsWeighted`, so harness and production disagree on which reason bucket 0 gets.
  - Some generated tests assert nothing about the SDK. For example, `TestGetOrRaise_GetOrRaiseCanRaiseAnErrorIfValueNotFound` only checks that the fixture key is absent from the store, and `assertGetWithDefault` implements the default semantics in the helper itself.
- Why it matters: A green contract suite does not show that the shipped client meets the contract. The type-casing divergence goes onto the wire to api-telemetry, which accepts any string (`telemetry-schemas.ts:34 type: z.string().optional()`), so downstream consumers see inconsistent casing across SDKs.
- Evidence: I captured the production telemetry POST from a real `Client` (httptest telemetry sink): `"summaries":[{"key":"ff","type":"feature_flag",...,"reason":2}]`, compared with the YAML's `type: FEATURE_FLAG`.
- Suggested fix: Point the generated helpers at a real `Client` built on the fixture data (datadir mode or an httptest delivery), capture telemetry from the real submitter, and delete `internal/eval`/`internal/resolver`. Normalize `type` to uppercase in `RecordEvaluation`.

### [MEDIUM] `ReturnZeroValue` only applies to timeouts; other init failures still return errors, contrary to the docs
- Where: quonfig.go:496 (`errors.Is(err, ErrInitializationTimeout)`), quonfig.go:1095-1108 (only `DeadlineExceeded` is normalized), options.go:460-463 ("if every leg times out (or otherwise errors) ... ReturnZeroValue makes them return zero values"), options.go:17-20
- What: When both legs return 503, 401, connection refused, or an invalid body, callers that chose `WithOnInitFailure(ReturnZeroValue)` still get `err != nil` from every getter.
- Why it matters: Code written against the documented contract, such as `if err != nil { return 500 }`, starts failing requests during a delivery outage. That is the scenario the option exists for.
- Evidence: With a 503 on both legs and `ReturnZeroValue`, the getter returned `v=false ok=false err=unexpected status 503 from http://127.0.0.1:50057: down`.
- Suggested fix: Apply `ReturnZeroValue` to any init failure, or correct the option docs.

### [MEDIUM] Type mismatch silently returns the zero value with ok=true and no error
- Where: quonfig.go:329-363 (getters call `val.BoolValue()`/`IntValue()`/...), config.go:52-100 (accessors return 0/false/"" or silently parse a string)
- What: `GetBoolValue` on a string config returns `(false, true, nil)`. `GetIntValue` on `"abc"` returns `(0, true, nil)`. `IntValue` on a float truncates.
- Why it matters: Wrong values are served silently, with no signal to the caller or in telemetry. The OpenFeature `TYPE_MISMATCH` code exists (quonfig.go:634-635) but is only produced for ENV_VAR coercion.
- Evidence: Code reading; the accessor bodies are shown at config.go:52-100.
- Suggested fix: Check `cfg.ValueType` (or the concrete Go type) in each typed getter and return an `ErrTypeMismatch` sentinel mapped to `ErrorCodeTypeMismatch`.

### [LOW] Hot-path work that does not need to be there
- Where: evalcore/operators.go:113 (`regexp.Compile` on every PROP_MATCHES evaluation), runtime_eval.go:33 and 19-25 (each evaluation, and each IN_SEG lookup, deep-converts the whole config into evalcore types), telemetry.go:103-110 (context maps are copied even when no context aggregator is enabled)
- What / why: At about 1µs and 13-21 allocations per call this is fine for most services. Regex-heavy or segment-heavy configs cost more for no reason. Go regexp is RE2, so there is no ReDoS risk.
- Suggested fix: Convert once at install time, and cache compiled regexes per criterion.

### [LOW] Dead and duplicated packages
- Where: internal/transport/client.go (no importers), internal/store (only its own test imports it), internal/eval + internal/resolver (test-only duplicates of runtime_eval.go/runtime_resolver.go, including a second copy of `reportableValueFor` and of the error sentinels), and `evalcore` is a public package, so it is part of the 1.x API
- Why it matters: Bug fixes must be made twice (qfg-9dxb.4 did exactly that for the decryptWith cycle), and the duplicates are what the contract suite tests (see the Medium finding above).

### [LOW] A zero-value `ContextSet` panics when used
- Where: context.go:24-35 (writes to a nil `data` map)
- What: `(&quonfig.ContextSet{}).WithNamedContextValues(...)` panics in the caller's goroutine, outside the evaluation recover boundary. `SetNamedContext(nil)` also panics.
- Suggested fix: Allocate the map lazily in the setters.

### [LOW] Unbounded body reads, and response bodies echoed into getter errors
- Where: runtime_transport.go:285-286 (`io.ReadAll` on a non-200 response, then embedded in the error), runtime_transport.go:290 (no size limit on a 200)
- What: A misbehaving proxy or WAF page ends up verbatim in `initializationErr`, which every getter returns and logs while init has failed. A huge body is fully buffered. The time is bounded (hedgeAbort 6s) but memory is not.
- Suggested fix: Use `io.LimitReader` for error snippets (1-4 KiB) and a generous cap for envelopes.

### [LOW] Possible secret leakage into error messages
- Where: runtime_resolver.go:63 (`ErrUnableToCoerce` includes the raw environment-variable value `%q`)
- What: If an ENV_VAR-provided config points at a secret with the wrong `valueType`, the secret appears in the returned error, in `EvaluationDetails.ErrorMessage`, and in any log line the caller or an OpenFeature provider writes.
- Suggested fix: Omit the value from the error message, or truncate and redact it.

### [LOW] Privacy defaults: raw context values sent to the vendor, and the developer context is on by default

Separately, on any host where someone ran `qfg login` (a bastion, a CI runner, a dev-built prod image), the developer's email is merged into `GlobalContext`, where it affects targeting and telemetry.

## Test suite assessment

- Size and health: 632 tests pass under `-race`, with no flakes observed in 1 full run and several targeted re-runs. 5 integration tests always skip under `-short`, and CI only runs `-short`.
- Contract coverage, spot-checked behaviors:
  1. Weighted consistency: get_weighted_values_generated_test.go asserts exact bucket values for 3 tracking IDs. This is real, but it goes through `internal/eval`, which does share `evalcore` with production, so it is meaningful for evalcore.
  2. ENV_VAR missing: get_or_raise asserts on the error from `internal/resolver`, not from `runtimeResolver`/`Client`.
  3. Get-or-raise not-found: the test only asserts that the fixture store lacks the key. **It cannot fail for an SDK bug.**
  4. Init timeout (`assertInitializationTimeoutError`): does drive a real `Client` with a blocking RoundTripper. Real.
  5. Telemetry eval summaries: fed through `internal/telemetry` aggregators with harness-computed reason, type and redaction. They pass while production sends a different `type` string (Medium finding).
- The generator (go.ts) states "NO auto-skips, NO omissions", and I found no `t.Skip` in the generated files. The case counts match the YAML (~187 generated test functions).
- Behaviors in this SDK that the shared suite does not cover at all: the hedge/failover state machine (covered by good local unit tests such as quonfig_hedge_test.go and ordering_guard_test.go, and by chaos), the SSE parser limits, `Close()` lifecycle races, callback re-entrancy, aliasing of returned values, partial-envelope tolerance, and the typed getters' type-mismatch behavior.
